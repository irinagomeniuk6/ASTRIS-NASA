# ASTRIS — передача проєкту розробнику

Версія застосунку: **1.7.0**. Стан описано **15 листопада 2026 року**.

Це основний документ для продовження роботи. Він описує поточний код, прийняті рішення й наступні завдання. Докладні формули та експерименти винесені в окремі файли, перелічені наприкінці.

## 1. Що ми робимо

ASTRIS — локальна наземна консоль для спостереження за фізіологічними показниками екіпажу під час тривалої космічної місії. Оператор бачить актуальні вимірювання, зміни в часі, прогнози й сигнали з поясненням розрахунку.

Проблема: набір поточних чисел не показує, чи розвивається небажана тенденція, чи дані застаріли і наскільки корисним виявилося попередження. Проєкт поєднує показники, контроль якості даних, математичний аналіз і перевірку результатів прогнозу.

Початкове завдання стосувалося здоров’я астронавтів і самостійної оцінки стану в тривалих місіях. У поточній ітерації власник обрав **наземного оператора** основним користувачем. Бортова версія для астронавта ще не розроблена. Для захисту слід прямо сказати, що готова саме наземна частина.

Наявний результат — дослідницький прототип для демонстрації та розширення. Він не підключений до справжнього обладнання, не встановлює діагнозів і не є сертифікованою системою життєзабезпечення.

## 2. Рішення власника, які потрібно зберегти

- Проєкт залишається **локальним**. Публікацію коду та розгортання на зовнішньому сервісі власник раніше відхилив. Не завантажувати проєкт чи дані назовні без окремого доручення.
- Працюємо з наявним стеком. Повне переписування на інший фреймворк не замовляли.
- Інтерфейс українською, темний, із графітовими та приглушеними лавандовими відтінками. Потрібні вільний простір, чітка ієрархія й короткі тексти.
- У меню чотири робочі розділи: **Огляд, Екіпаж, Аналіз, Сигнали**. Окреме **Демо** містить допоміжні експерименти. Не повертати вісім самостійних вкладок.
- Графіки входять до аналізу. Журнал відкривається із сигналів. Формули, оцінки помилок і додаткові таблиці розгортаються за потреби.
- Оператор не заповнює самооцінку за астронавта. Сон і самопочуття можуть надходити лише окремим повідомленням екіпажу.
- Межі показників задаються користувачем. Не вбудовувати вигадані фізіологічні норми або нормативи NASA.
- Прогноз має залежати від даних і перевірки моделей. Не додавати випадкові вигини лише для ефектного графіка. Пряма або сталий рівень теж можуть бути обґрунтованим результатом.
- Не приховувати помилки прогнозу та не видавати внутрішню синтетичну перевірку за клінічну точність.

## 3. Що передається

Архів `ASTRIS-project.zip` після розпакування містить готовий `ASTRIS.html`, вихідний каталог `dist/`, тести, скрипти складання й документацію. Структура архіву є коренем проєкту; обов’язкової зовнішньої папки-обгортки немає.

`ASTRIS.html` — зібраний результат для відкриття у браузері. **Редагувати слід файли в `dist/`, а потім виконувати складання.** Зміни лише в готовому HTML загубляться під час наступної збірки.

Папка `work/` у початковому робочому просторі містить історичні одноразові перетворення. Вона не потрібна для продовження роботи й не входить у комплект. Не запускати старі патчі повторно: частина з них не розрахована на повторне застосування.

Нові переносні скрипти в `scripts/` працюють без початкового робочого простору та без зовнішніх залежностей. Приховані службові каталоги, Git-історія, кеші й облікові дані не входять до архіву.

## 4. Швидкий запуск

### Готовий файл

Відкрити `ASTRIS.html` у сучасному браузері. Стилі, код, портрети й геометрія моделі вбудовані. Інтернет не потрібен для основних функцій. Зовнішні методичні посилання відкриваються лише за бажанням користувача.

### Розробка

Потрібен Node.js **18 або новіший**. Залежностей із npm немає; `npm install` не потрібний. Поточну перевірку виконано на Node.js 22.22.2 та npm 11.13.0. Нижню заявлену версію Node 18 окремо в цій передачі не перевіряли.

З кореня розпакованого проєкту:

```text
npm start
```

Адреса: `http://127.0.0.1:4173`. Сервер слухає лише loopback. Завершення — Ctrl+C.

Інший порт у PowerShell:

```powershell
$env:PORT = '4174'
npm start
```

Основні команди:

| Команда | Результат |
|---|---|
| `npm test` | Усі 104 тести модулів розрахунків і даних |
| `npm run build` | Створює `ASTRIS.html` у корені та перевіряє вбудовані ресурси |
| `npm run check:standalone` | Повторно перевіряє готовий HTML без його зміни |
| `npm run control` | Повторює контрольний експеримент, оновлює `CONTROL-RESULTS.json` |
| `npm run package` | Збирає HTML і новий `ASTRIS-project.zip` із кодом та документами |

За потреби можна вказати інший вихідний файл:

```text
node scripts/build-standalone.cjs ../ASTRIS.html
node scripts/package-project.cjs ../ASTRIS-project.zip
```

Усі шляхи цих двох аргументів відносні до поточного каталогу або абсолютні. Скрипт пакування не публікує файлів і не використовує мережу.

Складання розпізнає поточний формат тегів у `index.html`, вбудовує локальні CSS/JS, favicon та шість портретів. Якщо додати шрифти, інші зображення або ресурси через CSS `url()`, потрібно окремо розширити вбудовування й перевірку автономності.

## 8. Стан, час і потік даних

Стан сесії створює `E.create()`. Основні поля:

| Поле | Призначення |
|---|---|
| `version` | Версія схеми сесії, зараз 1; не дорівнює версії застосунку 1.7 |
| `now`, `ticks`, `seed`, `seq` | Час симуляції, номер такту, стан генератора й ID подій |
| `histories[crewId]` | Отримані вимірювання, впорядковані за часом вимірювання |
| `sensorSettings`, `sensorSettingsVersion` | Параметри каналів і міграція, зараз версія 2 |
| `references[crewId][key]` | Зафіксована особиста статистична база |
| `alerts`, `counters`, `log` | Сигнали, лічильники підтвердження, події |
| `scenarios`, `scenarioStart` | Сценарій кожного профілю та його початок |
| `transport` | Конфігурації, черга, лічильники й записи доставки |
| `leadtime` | Попередження, спостережені переходи та підсумки |
| `crewReports` | Окремі повідомлення екіпажу |
| `controlEvaluation` | Останній запуск контрольного набору |
| `daily`, `tasks`, старі `sleep/mood` | Сумісні залишки попередніх версій; не нова телеметрія |

Стартовий час — `2026-11-14 08:40 UTC`, початкова seed — `260114`. Це дата демонстраційної місії, а не поточний час комп’ютера. При запуску створюється 61 точка на профіль за попередні 60 хвилин.

**Один такт додає одну хвилину місії.** Швидкість 4/2/0,5 секунди змінює лише темп відтворення. При паузі час місії не йде. Нова сесія початково працює, відновлена зі сховища — на паузі.

Основний цикл браузера:

```text
E.tick(state)
  → час +1 хв, створення пакетів для всіх профілів
  → T.send: відправлення або втрата
  → T.flush: доставка готових пакетів до histories
  → базова оцінка поточних вимірювань
A.sync(state)
  → аналіз якості, тенденцій, аномалій, прогнозу та одночасності
L.observe(state)
  → нові прогнозні попередження та перевірка старих за фактами
persist()
render()
```

Пакети, які ще в черзі, **не входять у `histories` і не доступні прогнозу**. Не використовувати чергу для заповнення поточних показників або перевірки майбутніх результатів.

## 9. Контракти даних

### Пакет фізіологічних показників

```js
{
  ts: 1794645600000,             // Unix ms, час вимірювання
  hr: 73,
  sys: 116,
  dia: 76,
  spo2: 98.3,
  temp: 36.6,
  glucose: 101,
  quality: 'good',
  source: 'simulator',
  units: { hr: 'уд/хв', temp: '°C' } // необов’язково, без конвертації
}
```

При доставці додаються `measuredAt`, `sentAt`, `receivedAt`, `packetId`; `ts` зберігає час вимірювання. У початкової згенерованої історії цих транспортних полів може не бути — не вигадувати їх заднім числом.

`S.inspect(packet, key, now, config)` повертає якість, числове значення або `null`, час і причину. Нуль не замінює пропуск. Рядки, NaN, Infinity, неправильні одиниці та некоректні/майбутні часові мітки не є валідними вимірюваннями.

Пакетна якість: `good`, сумісне `manual`, `offline`, `invalid`. Похідні стани перевірки: `good`, `missing`, `invalid`, `future`, `stale`. Поле `quality: good` саме по собі не підтверджує справність реального датчика.

### Повідомлення екіпажу

```js
{
  reportId: 'report-unique-id',
  crewId: 'a2',
  authorCrewId: 'a2',
  reportedAt: 1794645480000,
  receivedAt: 1794645600000,
  source: 'simulator',           // або external-unverified
  values: { sleep: 7.2, mood: 4 },
  text: 'Текст повідомлення'
}
```

`O.receive` перевіряє ID, автора, послідовність часу та значення, відкидає дублікати `reportId`, додає запис у журнал. Сон — число 0–24, самопочуття — ціле 1–5; це шкала введення, не медична норма. Повідомлення **не змінює вимірювань**. Збережений запис має `identityVerified: false`; автентифікації немає.

### Сигнал

Сигнал містить `id`, `crewId`, `metric`, `origin`, `ts`, `lastSeen`, `lastValue`, `acknowledgedAt`, `resolvedAt`, `evidence`; за потреби `analysisType`, `ruleId`, `evidenceUnavailable`, `resolutionReason`.

`origin` розрізняє `configured`, `analysis`, `joint`, архівний `legacy`. `evidence` зберігає формулу та використані параметри/значення. Для спільного сигналу є масив доказів за каналами.

**Взяти в роботу ≠ завершити відхилення.** Ознайомлення прибирає сигнал із нових, але лишає його активним. Брак даних не доводить відновлення. Зміна правила або його вимкнення може завершити попередній сигнал із відповідною причиною, а не твердженням про безпечний стан.

## 10. Межі та математичні параметри

Параметри налаштовані **на тип показника для всього екіпажу**. Індивідуальна статистична база є, індивідуальних медичних меж на кожен профіль поки немає.

Початкові налаштування `S.defaults(key)`:

| Параметр | Значення |
|---|---|
| `min`, `max`, `maxRate` | `null` — вимкнені |
| `confirmationSamples` | 3 різні пакети для межі |
| `sigmaThreshold`, `sigmaFloor` | 3 та 0 |
| `movingAveragePoints` | 5 |
| `forecastMinutes`, `forecastLookbackMinutes` | 5 та 60 хв |
| `fitWindowMinutes` | 15 хв |
| `minFitPoints`, `minFitSpanMinutes`, `minCoverage` | 6, 5 хв, 0.8 |
| `expectedIntervalSeconds`, `maxAgeSeconds`, `maxGapSeconds` | 60, 180, 90 с |

Це інженерні параметри демонстрації. Не переносити їх у реальне обладнання як нормативи. Повтор тієї самої часової мітки не є новим пакетом для підтвердження.

Базові методи:

- Середнє, min/max, вибіркове стандартне відхилення `s = sqrt(Σ(x−mean)²/(n−1))`.
- Швидкість `Δx/Δt`; мілісекунди переводяться у хвилини. Розриви й помилки не з’єднуються.
- SMA за k точками та EWMA з α=0.2. Після пропуску згладжування починається заново.
- Фіксована база за першими до 30 валідними вимірюваннями. `z=(x−μ)/max(s, sigmaFloor)`. За нульової шкали z не визначається.
- МНК-тренд, адаптивний прогноз, історична перевірка MAE/RMSE/bias.
- Pearson для рівнів і швидкостей після одноразового часового зіставлення без інтерполяції. Кореляція не встановлює причинності.
- Окреме правило одночасних z-відхилень. Це не діагноз і не висновок про несправність скафандра.

За замовчуванням порівняння потребує 8 пар, повноти 80%, однакових часових міток; одночасність — щонайменше 2 канали у вікні 60 с. Опис стійкості використовує 3 послідовні точки. Налаштування — `A.configureResearch`.

`A.analyze` також готує базу/конфігурації в стані; це не повністю безпобічна функція над незмінним станом. Кеш прогнозу живе всередині `forecast.js`.

## 11. Як працює прогноз

Кандидати: останнє значення, лінійна регресія, згасаючий Голт, стабільна AR(2). Пам’ять моделі початково 60 хв і не дорівнює періоду видимого графіка.

На однакових минулих цілях порівнюються до 24 завершених перевірок. Для впевненішого вибору потрібно щонайменше 8 спільних перевірок. Складніша модель має зменшити RMSE базової щонайменше на 10%; у межах 5% від найкращого результату надається перевага простішій. За малої історії вибір попередній.

Голт має фіксовані α=0.5, β=0.2, φ=0.9. AR(2) потребує регулярного кроку та щонайменше 12 точок; нестійкі коефіцієнти відхиляються. Випадкові майбутні значення не домальовуються.

Окрема перевірка повторює весь вибір моделі на кожному минулому початку до появи цільового факту. Не плутати RMSE підгонки, RMSE таблиці вибору та RMSE цієї перевірки.

Діапазони використовують завершені помилки для відповідного горизонту. За достатніх умов та ≥19 помилок — емпіричний 95% ранг; за 5–18 — спостережений максимум без заяви про 95%. Для попередньої лінійної моделі можливий умовний інтервал Стьюдента. Статистичні припущення не доведено, майбутнє покриття не гарантовано.

Модуль може обґрунтовано обрати сталий рівень. Після нової зміни режиму він може запізнитись. Це потрібно вимірювати, а не приховувати красивою кривою.

## 12. Доставка, завчасність і контрольний набір

### Доставка

`T.configure(state, crewId, config)` задає затримку 0–30 хв, додаткову варіацію 0–10 хв і втрату кожного N-го пакета: 0 або 2–20. Варіація детермінована: N, 0, N/2. Черга зберігає вже надіслані пакети при зміні конфігурації.

Доставка перевіряється щохвилини, тому затримка 0.5 хв фактично дасть 1 хв. Статистика використовує реальний час отримання. Старий пакет доповнює минулу історію. Актуальність визначається за вимірюванням, а не за фактом щойно отриманого повідомлення.

### Завчасність

`L.observe(state)` зберігає перше відкрите прогнозне попередження за каналом і звіряє його з наступним виміряним переходом через задану межу в прогнозному вікні.

`leadMinutes = (actualCrossingMeasuredAt − warningIssuedAt) / 60000`

Фактичний перехід — два послідовні валідні вимірювання: всередині меж → поза межею. Точного фізичного моменту між ними не визначено. Доставка факту із запізненням не додає вигаданих хвилин випередження; результат може бути від’ємним.

Статуси: `pending`, `confirmed`, `not-confirmed`, `unverified`, `cancelled`. Сам плин часу не означає успіху чи помилки. Неповні дані не зараховуються до хибних сигналів; зміна параметрів скасовує незавершену перевірку. Окремо обліковуються спостережені перетини без завчасного попередження.

### Контрольний набір

`astris-control-v1`: шість окремих синтетичних рядів по 120 точок, seed 91001–91006. 72 початкові та 48 контрольних точок. Початки 71, 77, 83, 89, 95, 101, 107; горизонти +1/+5/+10 хв. На пізніших початках можна використовувати вже відкриті факти, але не майбутні цілі чи мітки викидів.

Виміряні результати в умовних одиницях:

| Горизонт | n | MAE | RMSE моделі | RMSE останнього значення | Покриття |
|---|---:|---:|---:|---:|---:|
| +1 хв | 40 | 1.078 | 3.348 | 3.351 | 90.0% |
| +5 хв | 39 | 1.929 | 4.756 | 5.173 | 84.6% |
| +10 хв | 40 | 2.454 | 5.538 | 5.141 | 82.5% |

На +5 хв RMSE нижча приблизно на 8.1%, на +10 хв — вища за базову. Це не універсальна точність моделі. На окремому ряді з трьома навмисними викидами: TP=3, FP=0, FN=0, TN=45. Це не оцінка виявлення хвороб.

Набір уже відомий розробникам. Для наступного незалежного висновку потрібні нові відкладені дані та заздалегідь визначений протокол. Не підлаштовувати модель під ці шість рядів і не називати повторну оцінку на них зовнішньою валідацією.

## 13. Зберігання, експорт і міграції

Ключ браузерного сховища: **`astris-demo-v1`**. Зберігається об’єкт `{ state, selected }`. Більшість стану екрана, зокрема відкрита вкладка демо та обраний показник аналізу, не є частиною цього контракту збереження.

Сховище залежить від origin і браузера. Файл, `127.0.0.1:4173` та інший порт не слід вважати однією сесією. Поведінка `localStorage` для `file://` залежить від браузера. При недоступному сховищі показується повідомлення; експорт залишається способом зберегти файл.

Міграції не видаляють вимірювання. Старі сигнали фіксованих демопорогів архівуються, поточні нормативні межі не вигадуються. Старі `sleep/mood`, `daily`, `tasks`, сумісний `E.checkin` і сценарій `fatigue` лишилися у коді/сирому стані. Вони не означають наявність форми самооцінки або безперервного датчика сну в інтерфейсі.

Ліміти: до 1440 пакетів на профіль, 150 подій журналу, обмежений список сигналів; 100 повідомлень екіпажу, 240 записів доставки, останні 100 затримок на профіль, по 240 записів попереджень і переходів для завчасності. Це не повний незмінний аудит місії.

JSON-експорт версії 1.7 включає отриману історію, конфігурації, аналітичні знімки, модели й оцінки прогнозу, спільні докази, повідомлення, стан доставки, завчасність, контрольні дані та сирий стан. `dataType` позначає синтетичну демонстрацію.

В експорті є черга вже виміряних, але ще не отриманих наземною аналітикою пакетів — як частина **симулятора**. Не видавати її за доступну оператору телеметрію.

**Імпорт сесії з JSON поки не реалізовано.** Експорт сам по собі не дає кнопки відновлення. Перед реалізацією імпорту потрібні схема, ліміти, перевірка версій і безпечна обробка вмісту.

`sw.js` реєструється тільки за HTTPS; поточний cache key `astris-offline-v10`. Для `file://` та звичайного локального HTTP він не є основою автономності. За зміни ресурсів оновлювати список кешу й його версію.

## 14. 3D та візуальні матеріали

Усі профілі використовують один процедурний манекен у A-позі. Це не скан конкретної людини й не анатомічна модель з медичними результатами. Обертання працює мишею та клавіатурою. Світіння/сітка — оформлення, не виміряний стан органів. Клікабельні анатомічні ділянки зараз не реалізовані.

`human-mesh.js` містить готову квантовану геометрію; `human-view.js` — декодування, шейдери й взаємодію. Позиції передаються як Int16 з масштабом 0.0001, нормалі — нормалізовані Int16, індекси — Uint16. При заміні геометрії потрібно дотримати цього контракту або одночасно змінити рендерер. Початковий процедурний генератор не є частиною підтримуваного процесу складання: для роботи застосунку готового mesh достатньо.

Портрети `a1.jpg`–`a6.jpg` — згенеровані зображення вигаданих дорослих людей, не фото справжніх астронавтів. Промпти й походження наведено в `ASSETS.md`. Для заміни портрета достатньо зберегти відповідний JPEG, потім виконати збірку.

Автоматичних браузерних E2E-тестів немає. У поточній версії вручну перевіряли меню, вибір датчика, графік, розгортання статистики, журнал, демо та старі маршрути. Після змін потрібні власні перевірки інтерфейсу. Локальні знімки екрана — ілюстрації, не заміна тестів.

Ручний мінімум після правки:

1. Огляд і шість карток екіпажу відкриваються; вибір профілю правильний.
2. В аналізі змінюються показник, період і горизонт. Графік підтримує навігацію клавіатурою.
3. Межі порожні у новій сесії; зміни валідуються. Перевірити тиск із двома незалежними компонентами.
4. «Взяти в роботу» не завершує активного відхилення. Журнал відкривається із сигналів.
5. При втраті або застарілості даних не показуються вигадані поточні числа; прогноз блокується.
6. Додавання тестового повідомлення не змінює телеметрію.
7. Контрольний набір відтворює таблицю вище. Експорт містить очікувані поля.
8. Після `npm run build` відкрити саме готовий HTML без сервера; перевірити портрети, WebGL або його fallback.

### Сцена для захисту: попередження до події

В окремій чистій демосесії: Маркус, пряма доставка, «Лінійний дрейф», три рази +10 хв. Пульс 118. Далі «Демо → Завчасність»: задати **умовну експериментальну** верхню межу 130 і прогноз 10 хв. Межа 130 наведена лише для перевірки алгоритму, це не фізіологічна норма. Ще +10 хв: перший перетин 131.5 на 39-й хвилині сценарію. У перевіреній сцені попередження випередило його на 9 хв.

Контрприклад: одразу після зміни режиму межа 100 з горизонтом 10 хв може перетнутися без завчасного попередження. Це враховується, а не приховується.

### Використання модулів без браузера

```js
const E = require('./dist/engine.js');
const A = require('./dist/analytics.js');
const O = require('./dist/operator.js');
const L = require('./dist/leadtime.js');

const state = E.create();
O.prepare(state);
A.references(state);
A.sync(state);
L.observe(state);

E.scenario(state, 'a2', 'drift');
E.tick(state);
A.sync(state);
L.observe(state);

const result = A.analyze(state, 'a2', 'hr', 60);
console.log(result.current, result.mean, result.rate, result.forecast.model);
```

Для зміни конфігурації використовувати `E.configure`, потім `A.sync` та `L.observe`, а не лише змінювати поле в об’єкті. Для повідомлення — `O.receive` або тестове `O.simulate`; для доставки — `T.configure`. У браузері ці API доступні як `AstrisEngine`, `AstrisAnalytics`, `AstrisOperator`, `AstrisTransport`, `AstrisLeadtime`, `AstrisBenchmark`. Основний стан інтерфейсу закритий у функції `app.js`, не є глобальним API.

## 16. Відомі обмеження й борг

Це перелік підтверджених обмежень реалізації, а не перелік уже виправлених функцій.

- Немає справжнього приймача телеметрії, backend API, спільного сховища чи синхронізації кількох операторів.
- Немає авторизації, перевірки особи автора повідомлення та захищеного незмінного журналу.
- Немає бортового клієнта, технічних сенсорів скафандра та медичної валідації.
- Немає імпорту сесії; перевірка збереженого `localStorage` поверхова, а не повна JSON-схема.
- Налаштування меж спільні для типу показника; індивідуальні протоколи ще треба спроєктувати.
- `app.js` великий, багато HTML формується рядками; дев’ять CSS-файлів містять історичні перевизначення.
- Розрахунки виконуються в основному потоці. Довгий крок +10 хв і контрольна перевірка можуть коротко навантажувати інтерфейс. Web Worker не реалізовано.
- Метрики й журнал обмежені останніми записами, а не всією місією. Завершені оцінки завчасності не перераховуються заднім числом через пізню доставку минулих пакетів.
- Контрольний набір невеликий і синтетичний. На частині горизонтів модель гірша за простий базовий прогноз.
- У коді є сумісні ручні поля/API та прихований у меню сценарій `fatigue`; їх не варто приймати за чинні можливості UI.
- Статус «Без сигналів» не дорівнює «Людина здорова». «Дані актуальні» не дорівнює «Датчик справний».

Окремо потрібно перевірити прийом кількох пакетів за один крок і довгі реальні сесії перед використанням з обладнанням. Поточна оцінка завчасності працює з послідовністю доступних поточних станів, а не з повною реконструкцією всіх фізичних переходів.

## 17. Що доробити далі

Пріоритети залежать від того, чи готуємо лише захист, чи починаємо реальний збір даних. Нижче — запропоновані наступні роботи, вони ще не виконані.

| Пріоритет | Робота | Критерій готовності |
|---|---|---|
| До захисту | Автоматизувати короткий браузерний сценарій | Усі чотири робочі розділи, демо, валідація меж, збереження й відсутні дані проходять повторювану перевірку |
